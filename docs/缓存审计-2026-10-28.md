## 0. 一句话结论

**面板 79.5% 不是"聊天缓存坏了一半"，而是三个不同口径叠出来的数：**
① 聊天稳态确实能到 **94~97%**，但那是 **10K 级长会话的单次值**；把 633 次新版聊天里"没有断点"的 374 次合起来算，命中率是 **90.5%**（因为每轮固定有 400~450 token 的易变尾巴，5~6K 的 prompt 上就是 6~8 个点）；
② 整体只有 **65.1%**，因为 **40.9% 的调用出现了"断点"**，平均每次断点要按全价重算 **3,962 个 prompt token**，6 天累计多花 **111.8 万 token ≈ ¥1.68**；
③ 面板分母里还有 **memory_merge / lexicon / utility / vision** 四个非聊天 scope（占 prompt 的 18.3%、命中率 0~44%），把聚合往下拽 2~4 个百分点。

断点的主因排序（6 天）：**慢块内容变化 50.6% · 进程重启冷启动 28.1% · TTL/空闲 9.4% · 会话切换 3.0% · 历史压缩 0.7% · 尾巴 8.2%**。
快照 TTL 上线后（P4，10-27 20:41 起）总量降到 78.8%，但**快照窗口内仍有 22 次断点**（占该阶段浪费的 60%），且**每次快照到期几乎必断**（7 次刷新 7 次断、平均浪费 7,401 token）——这是当前最值得打的点。

## 1. 口径与数据缺口（先对齐"79.5%"是怎么来的）

### 1.1 面板口径

`dashboard/index.html:932`：`hit = SUM(cached_tokens) / SUM(prompt_tokens)`，分子分母都取**当天、全部 provider、全部 scope**。
不是 `cached/total`，也不是"只算聊天"。这一点直接决定了为什么"聊天 96%"和"面板 79.5%"能同时成立。

### 1.3 数据缺口（必须写进结论）

1. **`token_usage` 从 2026-10-23 20:56 才开始有行**，`近 7 天`实际只有 **4.6 天**（10-23 20:56 → 10-28 12:01，6 个日期）。10-22 完全无数据。
2. **10-23 全天是 ark 通道**（475 次 ark 调用里只有 89,728 cached），ark 基本不回传 `cached_tokens`，那天的 14.1% 不代表 DeepSeek 缓存表现；10-24 起才是 DeepSeek 官方 + 新结构 prompt。

4. `token_usage.scope` 只有 `chat`，没有 gid。会话级归因是用 `chat_history.timestamp`（**UTC，+8h 对齐**）与调用时间做 ±90s 最近邻匹配得到的，**633/633 全部匹配成功**，但一次调用可能落在两个通道的交界上（见 §4.4 的不确定项）。

## 3. Q2：四个慢块的真实变更频率、字符数、失效方式

### 3.1 前缀结构与断点标尺（先把"整块失效"说清楚）

`_compose_chat_messages` 的布局是**一个 system 消息**（`stable`）+ 历史多轮 + 动态块 + 最新 user。
`stable` 由 7 段直接字符串拼接，**四个慢块在最后、顺序写死**：

```
security_prompt (56 字)
persona.md (1,479 字)
DESKTOP_PET_SETTING (46 字)          ← 以上 3 段 = 所有会话共享的静态前缀
private_prompt(104 字) / privacy_prompt(178 字)  ← 私聊/群聊在这里分叉
【规则】 (30 字)
living_preset (345 字)
STATUS_LEGEND (1,133 字)
────────── base_stable = 私聊 3,178 字 / 群聊 3,252 字 ──────────
lexicon_prompt        （群黑话，仅群聊）
human_lexicon_prompt  （活人词库，末 6 条）
archive_prompt        （长期档案，私聊 cap 1000 字 / 群聊 cap 500 字）
learn_prompt          （global_learn 自学，cap 1000 字）
────────── stable 结束 ──────────
历史多轮 → 回忆/近况 → 易变尾巴 → 最新 user
```

DeepSeek 前缀缓存是**逐字节前缀**+64 token 块对齐，所以**第 k 块一变，从它开始到 prompt 末尾全部失效**。

用实测 `cached_tokens` 众数反推标尺（字符→token 比例约 **0.65**，与代码里 `_est_tokens` 的 0.7 基本一致）：

| cached 众数（实测） | 对应断点 | 含义 |
|---:|---|---|
| 0 | 完全冷 | 冷启动/服务不可用 |
| 1,024 | 静态前缀末尾 | 跨 scope 切换（共享段只到 persona 结束） |
| 2,048 | base_stable 末尾 | 群黑话块变了（群聊）/ 私聊词库变了 |
| **2,176** | **archive 块起点** | **长期档案变了（最高频）** |
| 2,816 | learn 块起点 | 自学档案变了 |
| 3,456~3,584 | stable 末尾 | 慢块没变、历史段变了（压缩/重载/切会话） |
| 6,000~10,500 | 历史段中段 | 历史增长/会话长度不同 |

### 3.4 变更是否导致"整块前缀失效"——实测验证

- 指纹日志 22:32:01 记 `archive` 变 → **22:32:02 的调用 cached=2,176**（正好是 archive 起点）；
- 22:35:19 记 `archive` 变 → **22:35:20 的调用 cached=2,304**；
- 23:48:17 记 `learn` 变（同时 archive 变）→ 23:48:42 调用 cached=2,304（断在 archive）；

→ **是，整块失效，而且失效范围包含它后面的全部历史**。所以"改一个 100 字的黑话词条"的代价是 3.5~8K token 的全价重算，不是 100 字。

## 4. Q3：「内容变化 / 顺序变化 / TTL 到期」三类失效各占多少

### 4.1 判定方法（写清楚，方便复核/推翻）

对 633 次新版 DeepSeek 聊天调用逐次判定：

1. **断点**：`prompt - cached > max(900, 45% × prompt)`。900 是"尾巴"下限（易变尾巴 + 最新 user 实测 320~450 token + 客户端消息开销）。
2. **浪费**：`max(0, uncached - 尾基线)`，尾基线取该会话稳态命中（hit≥90%）的 uncached p25：私聊 367、group_904978774 326、group_187950638 436、group_362611694 310、group_1109975771 204。
3. **归因优先级**：
   - 调用落在某次进程重启后 15 分钟内 → 冷启动·进程重启；
   - 该 scope 在调用前 60 秒内有 `[缓存] 历史超预算` → 顺序变化·历史压缩；
   - 相邻同 scope 调用 `|Δprompt| ≥ 1500`（明显换了另一条会话）→ 顺序变化·会话切换；
   - 同 scope 上次调用 > 1 小时 → TTL 到期·空闲；
   - 同 scope 上次调用 600s~1h → 内容变化·快照到期重建；
   - 其余（≤600s 仍断）→ 内容变化·轮内慢块/服务端抖动。

## 7. 不确定项 / 建议下一步（审计只出结论，不动代码）

1. **P4 的 10.5K 长会话每轮断在 2,176**（占该阶段窗口内浪费 60%）——现有日志无法区分"双通道共用 scope / 快照键失效 / 服务端驱逐"。新代码日志已带 `scope=<gid>`，建议再补 3 个字段（只加日志、不改逻辑）：`snapshot_age`、`slow_fp=(lexicon,human,archive,learn)`、`hist_len`。跑一个活跃日后即可定性。
