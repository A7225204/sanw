# 缓存优化方案对比（2026-10-28）

> 依据：`docs/缓存审计-2026-10-28.md`（t1，只读审计）。
> 本文只做设计与取舍，**不含代码改动**；所有"改法"都指到具体文件/函数，供后续实现任务直接照做。
> 三个必选方案 A/B/C + 一个前置方案 D（会话身份/快照一致性），最后给组合账本与推荐顺序。

---

## 0. 结论先行

**推荐组合：A（内容哈希 + 延迟发布）+ D（身份/快照一致性，先诊断后修）+ B1（前缀内按 churn 重排）+ 调参（history↑ / tail↓）+ 非 chat 块改造。C 不默认做，只作为阈值触发时的逃生舱。**

一句话理由：
- **A 是唯一能同时降"断点频率"和"断点成本"的改动**，且不改任何人设/记忆内容（只改"什么时候把新文本换上前缀"）。
- **D 是审计里最大的单点**（P4 窗口浪费的 60% 来自同一条 10.5K 会话），但根因未定，必须先加日志确认再改；否则 A 的收益会被它吃掉。
- **B 是几乎零风险的顺风车**（收益 +0.6~1.3K token/次断点），但不解决问题。
- **C 在 A 落地后是净亏的**：把慢块挪到尾部 = 每次调用固定多付 1.1~1.3K token，换掉的只是"每次断点省 6K"；A 把断点频率降到很低后，这笔固定税就亏了。只有在"无法延迟发布（记忆必须实时）"或"churn 极高（10-24 那种每 2 次调用就变）"时才划算。

预期结果（算式见 §6）：

| 指标 | 现状 | A+D+B1（期望） | 再叠加非 chat + tail 压缩（期望/高值） |
|---|---:|---:|---:|
| P4 阶段 chat 命中 | 78.8% | 89.7%（区间 87~92） | 91~93% |
| 10-27 全站聚合（面板） | 77.3% | 85.8%（区间 84~88） | **88~90%（高值 91）** |
| 稳态单次命中（10K 会话） | 96.6~96.9% | 97.0~97.3% | **97.5~98.0%** |

> 注意 1：**"稳定态 ≥97%"不是靠消灭断点就能到的**。稳态命中 ≈ 1 − 尾巴/ prompt；当前尾巴基线 323 token、平均 prompt 5,982 → 94.6% 上限。要到 97%，必须同时把分母做大或把尾巴压小（§6.4 给三条路和算式）。
> 注意 2：**聚合 90% 是"可达但很紧"的**。10-27 口径下需要比现状多 cached **194,824 token**；A+D+B1+非 chat 的期望只能拿到约 153,800，加上 tail 压缩到 164,300，仍缺 ~30K（约 2 pt）。必须 A/D 取高值（或额外做 C-single、非 chat 抬到 90%）才够（§6.3 的缺口分配表）。

## 1. 基线与算式约定

### 1.1 记号

| 符号 | 含义 | 实测值（t1） |
|---|---|---:|
| P | 单次 prompt token | 平均 5,982；P4 阶段 8,398；10.5K 会话 ≈10.5K |
| T | 尾基线（易变尾巴 + 最新 user + 消息开销，**永远不缓存**） | 323（分会话 204~436；10.5K 会话 ≈400） |
| S | 四慢块合计 token | 私聊 1,347（lexicon 0 + human 115 + archive 651 + learn 581）；群聊 1,119 |
| B | 一次断点的额外 token（= 断点位置到 prompt 末尾 − T） | 平均 3,962；P4 阶段 6,108 |
| λ | 单次调用发生断点的概率 | 六天 40.9%；P4 阶段 23.2%（33/142） |
| N | 调用次数 | 六天 633；P4 142；10-27 全站调用 294 |

### 1.2 核心公式

```
单次请求命中率      = 1 − uncached / P
稳态（零断点）命中  = 1 − T / P
一次断点的额外成本  = B − T   ≈ 3,600~7,700 token
期望浪费（每次调用）= λ × (B − T)
方案增益 Δtoken     = N × (λ_before − λ_after) × (B − T)
聚合口径换算        1 pt = 15,380 token（10-27 样本：total_pin 1,538,000 / 100）
稳定态命中提升      = T/P 的下降量（P↑ 或 T↓）
钱                  = Δtoken × 1.5 元/百万（未命中 2.0 − 命中 0.5）
```

### 1.3 两个锚点基线（后面所有增益都按这两个算）

**锚点 1：P4（当前架构，10-27 20:41 → 10-28 12:01）**
142 次调用 / prompt 1,192,625 / cached 939,648 / 命中 78.8% / 可优化浪费 201,580 token，其中：
- 快照窗口内断点 22 次，121,381（60.2%）→ 其中 9 次是 10.5K 异常会话，72,892（36.2%）
- 快照到期重建 7 次，51,807（25.7%）
- 空闲 >1h 3 次，22,222（11.0%）
- 首次 1 次，6,170（3.1%）

**锚点 2：10-27 全天（面板口径）**
chat prompt 1,454,477 / cached 1,148,032 / 命中 78.9%；非 chat prompt 83,517 / cached 41,344；全站 77.3%。
→ 要全站 90%，chat 需要 **92.3%**（= (0.90×1,538,000 − 41,344) / 1,454,477）；chat 96% 则全站 93.4%。

## 2. 方案 A：慢块内容哈希快照 + 延迟发布（核心）

### 2.1 现状问题

`ai_group.py:2307-2427` 现在是**纯时间快照**：

```python
_snap = _SLOW_SNAPSHOT.get(_snap_key)
if _snap is not None and now - _snap[1] < SLOW_SNAPSHOT_TTL:   # 600s
    slow_text = _snap[0]        # 复用旧文本
else:
    slow_text = 4 个慢块直接拼接  # 到期就重建（不管内容变没变）
    _SLOW_SNAPSHOT[_snap_key] = (slow_text, now)
```

两个问题：
1. **到期就重建**，哪怕内容一字未变（重建结果字节相同，不产生断点，但浪费一次拼接，且日志无法区分"到期"和"变更"）。
2. **到期时如果内容变了，立刻换文本 = 立刻断前缀**，而且换的时机由"用户回来的时间"随机决定——常常正好是用户连续发消息的第 1 条，代价 6~8K token。P4 实测：快照到期 7 次、7 次全断。

### 2.2 具体改法

**文件**：`plugins/ai_group.py`，只动 `build_prompt_parts`（2307~2427）和几个模块级常量/字典。
**性质**：纯状态机，不碰人设、不碰记忆内容、不碰数据库。

```python
# 模块级（替换 _SLOW_SNAPSHOT）
_SLOW_STATE: dict = {}   # key(str(gid), is_private) -> dict(
                         #   text=已发布文本, fp=sha1, published_at=ts,
                         #   last_call=ts, pending=(fp, raw_text, since) | None)
SLOW_MODE       = os.getenv("PROMPT_SLOW_MODE", "hash")        # hash(新) | ttl(旧) | off(每轮现拼)
SLOW_MAX_STALE  = float(os.getenv("PROMPT_SLOW_MAX_STALE", "1800"))   # 积压上限（秒）
SLOW_IDLE_GAP   = float(os.getenv("PROMPT_SLOW_PUBLISH_GAP", "600"))  # 多久没调用算"自然断点"
```

`build_prompt_parts` 里把"取快照"改成"取已发布文本 + 记录积压"：

```python
raw = "".join(b for b in (lexicon_prompt, human_lexicon_prompt(),
                          archive_prompt, learn_prompt) if b)
fp = hashlib.sha1(raw.encode("utf-8")).hexdigest()[:12]
st = _SLOW_STATE.get(_snap_key)
now = time.time()
if SLOW_MODE == "off" or st is None:                 # 冷启动 / 关闭开关
    text = raw
    _SLOW_STATE[_snap_key] = dict(text=raw, fp=fp, published_at=now,
                                  last_call=now, pending=None)
elif SLOW_MODE == "ttl":                             # 旧行为，可一键回滚
    ...保持现有逻辑...
elif fp == st["fp"]:                                 # ★ 内容没变：永不换文本、永不"到期"
    text = st["text"]; st["pending"] = None
else:                                                # 内容变了：先积压，等断点
    if st["pending"] is None:
        st["pending"] = (fp, raw, now)
    pend_since = st["pending"][2]
    idle  = now - st["last_call"] > SLOW_IDLE_GAP
    stale = now - pend_since > SLOW_MAX_STALE
    if idle or stale:                                # 只在"本来就要断"或"积压超时"时发布
        st.update(text=raw, fp=fp, published_at=now, pending=None)
        logger.info(f"[缓存] 慢块发布 scope={gid} 原因={'idle' if idle else 'stale'} "
                    f"fp={fp} 积压={now-pend_since:.0f}s")
    text = st["text"]
st["last_call"] = now
stable = base_stable + text
```

要点：
- **内容不变 = 永不"到期"**，彻底去掉"纯 TTL 触发的重建"。
- 内容变了先**积压**，只在两种时机发布：
  1. `idle`：这个会话已经空闲 ≥600s（用户回来第一条，本来就要吃一次冷启动/半冷启动，发布不额外加价）；
  2. `stale`：积压超过 30 分钟（记忆新鲜度兜底，保证最多陈旧 30 分钟）。
- 两个阈值都走 env，可单独调、可一键关。
- 兼容：`_SLOW_STATE` 仍按 200 条上限回收；`_SLOW_SNAPSHOT` 保留给 `SLOW_MODE=ttl`。

### 2.3 预期增益（算式）

A 只影响"内容变化类断点"。P4 该类 = 29 次（22 窗口内 + 7 到期），173,188 token；其中 9 次/72,892 是 10.5K 异常（归 D，A 不动它）→ **A 的可作用池 = 20 次 / 100,296 token**。

发布策略把"每次变都断"变成"每 30 分钟最多断一次"：
- 活跃窗口里 λ_content 从 20/142 = **0.141** 降到约 0.03~0.05（6 小时活跃 ×2 次/小时上限，实际被 idle 断点吸收一半）；
- 保守取 60% 转化率：`Δtoken = 100,296 × 0.6 ≈ 60,000`。

| 场景 | Δtoken | chat Δ | 聚合 Δ（10-27 口径） |
|---|---:|---:|---:|
| 低（转化 40%） | 40,000 | +2.8 pt | +2.6 pt |
| **中（转化 60%）** | **60,000** | **+4.1 pt** | **+3.9 pt** |
| 高（转化 80%，异常也会被 idle 吸收） | 80,000 | +5.5 pt | +5.2 pt |

钱：60,000 × 1.5/1e6 ≈ **¥0.09**（P4 期间）；省的钱不多，主要价值是命中率和首字延迟。

### 2.4 复杂度与风险

- **复杂度：低**。约 40~60 行改动 + 3 个 env；无 schema 变更、无迁移、无新依赖。
- **人设/记忆质量影响：小且可控**。文本内容完全不变（还是四个慢块的原样拼接），只是"最多晚 30 分钟生效"；四个块里只有 archive 会分钟级变化，而 archive 是"长期记忆"，晚 30 分钟注入不影响长期事实；lexicon（群黑话）晚半小时影响"合群感"，可接受。
- **风险点**：
  1. 发布时机若卡在用户正在连续对话中（idle 判断失效），会多一次断点 → 有 stale 上限兜底，最坏退化回现状。
  2. 多进程/多实例时 `_SLOW_STATE` 不共享（见 D）。
  3. 积压期间如果同一 scope 有两条会话（QQ/飞书），可能各自发布不同版本 → 由 D 解决；A 本身不引入新问题。
- **观测**：新增日志 `[缓存] 慢块发布 scope=... 原因=idle|stale 积压=Xs`，可直接统计每日发布次数与命中率相关性。

### 2.5 回滚

```ini
# .env 一行回滚（改完重启进程即可，无需改代码）
PROMPT_SLOW_MODE=ttl     # 回到 10-27 的纯 TTL 行为
```
彻底回滚：`copy plugins\ai_group.py.bak_slowsnap_20261027 plugins\ai_group.py`（部署前先备份为 `bak_hashsnap_<日期>`）。

### 2.6 验收

1. 同一 scope 连续 20 次调用里，`慢块发布` 次数 ≤ 2；
2. 稳态（gap<600s 且非首调）命中 ≥ 96.5%（A 单独）；97% 需要再叠加 §6.4 的分母/尾巴策略；
3. 发布当次断点成本与现状同量级（不出现"发布风暴"）。

## 3. 方案 B：按变更频率重排块顺序

任务描述里的"把高频块挪到稳定前缀之后"有两种落法，收益差别很大，分开写：

### 3.1 B1：前缀内按 churn 升序重排（推荐，顺风车）

**现状顺序**（`ai_group.py:2420-2422`）：`lexicon → human_lexicon → archive → learn`
**问题**：改一个块会把**它后面所有块 + 全部历史**打掉。所以"高频块越靠后，单次断点越便宜"。

**改法**（3 行）：

```python
if is_private:
    slow_text = "".join(b for b in (human_lexicon_prompt(), learn_prompt, archive_prompt) if b)
else:
    slow_text = "".join(b for b in (human_lexicon_prompt(), learn_prompt,
                                    archive_prompt, lexicon_prompt) if b)
```

依据（t1 变更频率）：私聊 archive 最频（活跃时 6 分钟 2 次、36 分钟 22 次）、learn 每天 1~2 次、human 6 天 1 次；群聊 lexicon 最频（活跃群一天几十次 top5 变动）、archive 次之、learn 每天 1~2 次、human 几乎不变。

**增益算式**：只省"被改块后面的块"的 token。
- 私聊 archive 变：现状后面还有 learn 581 → 重排后 archive 最后，**每次省 581**；
- 群聊 lexicon 变：现状后面有 human+archive+learn（115+325+581≈1,021）→ 重排后省 1,021；
- 代价：私聊 learn 变（每天 1~2 次）会多打掉 archive（+651）——频率低，净赚。
- P4：20 次内容断点 × 581 ≈ **+11,600 token = +1.0 pt chat**；群聊多的时候更明显。
- 六天口径：约 259 次断点里内容类约 179 次 × 0.7K ≈ **+125K token = +2.4 pt 全站**（乐观上界，含群聊）。

**复杂度/风险/回滚**：极低（3 行，纯字符串顺序）。风险是"部署当次有一次断点"（字节变了），可忽略。回滚 = 还原这 3 行 / 环境变量 `PROMPT_SLOW_ORDER=legacy` 可选。

### 3.2 B2：把高频块挪到"前缀之后"（= 对个别块做 C）

见 §4：这不是"重排"，而是"移出前缀"。**不建议默认做**，理由同 C。

### 3.3 结论

B1 值得做，但只有 1~2.4 pt，属于"顺手"，不要拿它当主方案。B2 与 C 合并评估。

## 4. 方案 C：易变内容改为请求尾部注入

### 4.1 改法

好消息：**管道已经现成**。三个聊天入口（`ai_group.py:6175` 私聊、`7028` 群聊、`7385` 飞书）都写了：

```python
extra_blocks: list = list(sys_slow)   # "慢变块放历史之后，前缀才能稳定"
```

而 `build_prompt_parts` 目前永远返回 `slow_blocks=[]`（2428 行注释：保留返回结构）。所以 C 的代码改动只有 **3 行**：

```python
# build_prompt_parts 末尾
slow_blocks = [b for b in (lexicon_prompt, human_lexicon_prompt(), archive_prompt, learn_prompt) if b]
stable = base_stable            # 不再拼 slow_text
return stable, volatile, slow_blocks
```

（配合删除/保留快照逻辑：C 模式下快照没意义，直接 `PROMPT_SLOW_MODE=off`。）

### 4.2 增益算式（为什么默认不划算）

C 是**用"每次固定税"换"断点成本"**：

```
每次调用固定多付 S token（慢块进了尾部，永远不缓存）
每次内容断点省下 B − T（因为前缀不再被慢块打断）
判据：λ × (B − T)  >  S   →  C 划算
```

| 场景 | λ（每调用断点率） | 每次断点浪费 B−T | 左边 λ×(B−T) | S | 结论 |
|---|---:|---:|---:|---:|---|
| 10-24 旧结构（每 2 次调用断一次） | 0.49 | ≈2,860 | 1,402 | ≈1,200 | 略赚（+200/次） |
| P4 现状 | 0.204 | ≈6,108 | 1,246 | 1,347 | **亏 101/次** |
| A 落地后 | ≈0.05 | ≈6,108 | 305 | 1,347 | **亏 1,042/次** |

P4 实测反推：若 C 上线，142 次 × 1,347 = 191,274 token 的固定税，只换回约 100,296 的断点节省 → **净亏 ~91K token（chat −7.6 pt）**。
六天口径：633 × 1,347 = 852,651 固定税 vs 565,611 断点节省 → 净亏 287K。

### 4.3 什么时候该用 C

1. **A 因质量要求不能延迟发布**（例如主人明确要求"刚记住的事下一句就得用上"）；
2. **λ 特别高**（某个块每 2~3 次调用就变、且没有自然断点可蹭）；
3. **兜底逃生舱**：A 上线后如果某块仍然制造 >1 次/8 调用的断点（`λ > S/(B−T)` ≈ 0.24），再单独把**那一个块**挪到尾部，其余留在前缀。

**增量变体 C-single（推荐作为逃生舱形态）**：只移 archive（`S=651`，私聊阈值 λ>0.11），lexicon 只对 churn 高的群移（S=98，阈值 λ>0.017）。代码上就是把 `slow_blocks.append(archive_prompt)` 而不是返回全部。

### 4.4 复杂度/风险/回滚

- 复杂度：低（3 行 + 删快照）。
- 人设/记忆质量：**提升**（每次都是最新记忆，零陈旧）。
- 风险：**成本上升**——尾部每轮全价，长会话每轮多 1,347 token ≈ **¥0.0027/轮**（2 元/M 全价 vs 0.5 缓存）；六天多付 85 万 token ≈ ¥1.28；同时 prompt 变长会提高首字延迟（尾部在最后，影响小）。
- 回滚：`PROMPT_SLOW_MODE=ttl` 或还原 `return stable, volatile, []`。

### 4.5 结论

**不默认做。** 审计数据不支持"把慢块全部挪到尾部"——它只适合 10-24 那种"几乎每轮都变"的病态阶段。正确顺序是 A 先把 λ 压下去，再看是否需要 C-single。

## 5. 方案 D：会话身份 / 快照一致性（前置，不是可选项）

### 5.1 为什么必须先做

t1 审计最大单点：P4 的 33 次断点里 17 次属于同一条 10.5K 会话；22 次窗口内断点里 9 次是它（72,892 token = P4 浪费的 36%、窗口内浪费的 60%）。而同一时段另一条 6.5K 会话稳定 94~95%。同一 scope、同样 base，一条稳一条每轮断，说明**"这个 gid 的 stable 前缀在两次调用之间变了"或"快照没有被复用"**。现有证据不足以区分三种可能：

1. 同一逻辑会话被两条渲染路径/进程各自维护历史（QQ 私聊 + 飞书私聊。已确认 `FEISHU_OWNER_UID=100000000`，两条路都落到 `gid="private_100000000"`；若飞书桥是独立进程，就会出现两份 `_history` + 两份 `_SLOW_STATE`，且都写同一个 archive 文件）；
2. `_SLOW_SNAPSHOT` 在某些情况下没生效（键不稳定 / 被 200 条上限挤掉 / 进程重启清空）；
3. 服务端缓存条目被驱逐（证据不支持：驱逐通常回到 0 或 1,024，而它稳定停在 2,176）。

### 5.2 先诊断（1~2 天，只加日志）

`ai_group.py:2433` 的块指纹日志已带 `scope=`，再补 3 个字段：

```python
logger.info(
    f"[缓存] 块指纹 scope={gid} private={int(bool(is_private))} "
    f"lexicon={_fp8(lexicon_prompt)} human={_fp8(human_text)} "
    f"archive={_fp8(archive_prompt)} learn={_fp8(learn_prompt)} "
    f"snap_age={now-st['published_at']:.0f} pending={int(bool(st['pending']))} "
    f"hist_len={len(hist)} hist_tok={_history_tokens(hist)} pid={os.getpid()}"

```

有了 `pid` + `hist_len` + `snap_age`，一次活跃对话就能定性：
- 两个 pid 交替 → 双进程（D1）；
- 同 pid 但 `snap_age` 每次 <600 仍断 → 快照没复用/文本变了（D2）；
- `hist_len` 在两次调用间减少 → 压缩/重载（已知类）。

### 5.3 两种修法（按诊断结果二选一）

**D1 单实例化**（若是双进程）
- 让飞书桥走 IPC/内部调用（现在 `feishu_bridge.py:81/217` 已经是 `_run_async(ai_group.feishu_chat(...))`，理论上同进程；若实际是独立进程，改成同进程或加文件锁让只有一个进程持有 `gid` 的 `_history`）。
- 收益：消除 9 次异常断点 = 72,892 token（P4），chat +6.1 pt，聚合 +4.7 pt。

**D2 快照落盘 + 版本号**（若是多进程或多入口）
- 把 `_SLOW_STATE` 持久化到 `memory/prompt_snapshot.json`（key → text/fp/published_at），写入用现有的 `_save` 风格（临时文件 + 替换）；键统一用 **mem_scope**（`private_100000000` / `group_<gid>`）而不是 gid，保证 QQ/飞书同一条逻辑会话共享同一份已发布文本。
- 收益：把"两条会话各自发布不同版本"变成"共享一份"，切换不再互相打脸；估计回收 50~70% 异常断点（36~51K，chat +3~4 pt）。
- 风险：多进程写同一文件 → 用文件锁 + 只写不读缓存的短临界区；或直接改成 D1（更干净）。

### 5.4 复杂度/回滚

- D1：低~中（取决于飞书桥进程模型）；D2：中（约 60~80 行 + 一个小文件）。
- 回滚：`PROMPT_SNAP_PERSIST=false`（D2）；D1 回滚 = 恢复启动脚本。
- 人设/记忆质量：无影响（只是让两条通道看到同一份"已发布快照"；历史合流本来就是设计意图——`feishu_chat` 注释写明"写回同一份 QQ 记忆"）。

### 6.4 "稳定态 ≥97%" 的三条路（这是全站的硬约束）

稳态命中 = 1 − T/P。当前 T≈323、P 中位 5,982 → **94.6% 上限**；10K 会话单次 96.6~96.9%。

| 做法 | 算式 | 结果 |
|---|---|---|
| P 从 6.0K → 10.5K（历史预算 9000→12000，实际 ~0.65 tok/字） | 1 − 323/10,500 | **96.9%** |
| P → 14K（预算 →16000） | 1 − 323/14,000 | **97.7%** |
| T 323 → 250（砍一条易变尾巴 / 合并短行） | 1 − 250/10,500 | **97.6%** |
| 两者都做（P=12K、T=250） | 1 − 250/12,000 | **97.9%** |

- **history↑ 的成本**：多出来的历史全是缓存价（0.5 元/M）而非全价（2.0），且能提高记忆质量，属于"花小钱买命中率+质量"；但同时会**放大每次断点的成本**（B ∝ P），所以必须 A 先落地把断点频率压下来，再拉长历史。
- **tail↓ 的风险**：易变尾巴承载"今日状态/情绪/关系/别复读"等，压太狠会掉活人感；建议只做无损压缩（去重复标签、合并两行、把固定文案挪回 STATUS_LEGEND），**不删语义**——与 t1 审计里 10-25 那次 t4/P1-2 的做法一致。

## 8. 明确不做的（反模式）

1. **不要为了命中率删记忆/人设**：四个慢块的文本原样保留，A/B 只改"何时换"和"换的顺序"；C 改的是"放哪"，也不删内容。
2. **不要每轮重建快照**（等于回到 10-24，λ→0.5）。
3. **不要把易变状态（今日心情/情绪/关系/时间）塞回 system 前缀**：那是 10-25 之前的老问题，t1 已确认 stable/volatile 拆分的收益。
4. **不要默认全量 C**：P4 实测净亏 91K token（§4.2）。
5. **不要在 D 未定性前动 archive 的注入方式**：根因可能是"两条会话共用 scope"，改 archive 只会掩盖问题。
6. **不要用"每 10 分钟刷新"当卖点**：A 的语义是"内容不变不换、变了挑时机换"，TTL 只作为最大陈旧兜底。
