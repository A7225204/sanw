## 1. 口径、时间窗与 SQL

### 1.1 面板口径

面板"缓存命中率"= `sum(cached_tokens) / sum(prompt_tokens)`，全 provider × 全 scope，按当天聚合（`dashboard/index.html:932`，t1 已核对）。本报告全部数字用同一口径，**加权**（不是各轮百分比的算术平均）。

### 1.2 改前/改后切点与被测构建

- **被测构建**：`plugins/ai_group.py` mtime `12:26:37`（375,825 B），进程 `pid=6200` 于 `12:37:42` 启动 —— 跑的就是这份文件，无"改了没生效"。
- 该进程的日志在 `13:06:08` 被轮转为 **`logs/bot_restart.out.20261028_1306.log`**（12:37:42~13:06:08，含全部 49 条块指纹）。
- 第一条带 channel 的 chat 调用：`12:39:58`（qq）；飞书 `12:51:16`；最后一条 `13:01:40`。**本报告全部改后数字 = `12:37:42 ~ 13:01:40` 这一段的 pid 6200 构建。**
- ⚠️ **13:05:11 engineer 的 t6 修复（F1/F2/F3）已落盘、13:06:22 主人主动追加 persona「红线」段（4,147→4,893 B）、13:06:27 新进程启动** —— 本报告的结论**不覆盖** 13:06 之后的构建，需要复测（见 §8.2 第 1 条；边界处理见 §7.5）。
- `token_usage.channel/gid` 是 t3 新增列，**只有 12:39:58 之后的行有值**；改前行为空，不能按通道拆。

### 1.3 核心 SQL

```sql
-- 按天：chat 单独 / 全 scope
SELECT date, scope, SUM(prompt_tokens) p, SUM(cached_tokens) c, COUNT(*) n
FROM token_usage GROUP BY date, scope ORDER BY date;

-- 任意窗口（改前/改后）加权命中率
SELECT COUNT(*), SUM(prompt_tokens), SUM(cached_tokens),
       ROUND(100.0*SUM(cached_tokens)/SUM(prompt_tokens), 2)
FROM token_usage
WHERE ts >= '2026-10-25' AND ts < '2026-10-28' AND scope='chat';

-- 改后窗口分通道
SELECT channel, COUNT(*), SUM(prompt_tokens), SUM(cached_tokens)
FROM token_usage WHERE ts >= '2026-10-28 12:37:42' AND scope='chat' GROUP BY channel;

-- 逐轮（每轮一行，配合日志慢块指纹）
SELECT ts, prompt_tokens, cached_tokens, completion_tokens, channel, gid
FROM token_usage WHERE scope='chat' AND ts >= '2026-10-28 12:37:42' ORDER BY ts;
```

日志侧（逐轮前缀状态）：

```
[缓存] 块指纹 scope=… channel=… lexicon=… human=… archive=… learn=…
        slow_fp=… pub_fp=… snap_hit=… snap_age=… pend=… pub=… pub_reason=… hist_len=… hist_tok=… prefix_tok=… pid=…
```

释义：`slow_fp` = 四个慢块**现拼内容**的 sha1；`pub_fp` = **已发布（真正进 prompt）**文本的 sha1；`snap_hit=1` = 这一轮沿用上轮已发布文本（前缀没动）；`pend=1` = 内容变了但还压着没发布；`pub` = 该会话累计发布次数。

## 5. 稳定态 97% 未达标的根因（算术）

稳态命中率 = `1 − T/P`：

- 实测 **T = 448（中位）/ 467（均值）**；其中稳态 46 轮平均 **445 tok/轮**（易变尾巴 + 最新一句 + 64 token 对齐余量），冷启动/话题块另算；
- 实测 **P 中位 14,077**（窗口内 hist_tok 中位 9,674、从 8,382 长到 10,965；stable 估 3,881 + 尾巴）。

要 97%，需要 `P ≥ T/0.03`：

| T | 97% 需要的 P | 当前 P | 差 |
|---:|---:|---:|---:|
| 448（中位） | 14,933 | 14,077 | **+856/轮** |
| 467（均值） | 15,567 | 14,077 | **+1,490/轮** |

而 P 不是想涨就涨：`HISTORY_TOKEN_BUDGET_PRIVATE=12000` 且压缩是"超预算→压到 70%"的锯齿，history 只在 **[8,400, 12,000]** 之间摆动，对应 P 包络 **[≈12,885, ≈16,485]**：

| history 位置 | P（=hist+4,485） | T=448 | T=467 |
|---|---:|---:|---:|
| 8,400（刚压缩完） | 12,885 | 96.52% | 96.38% |
| 10,200（锯齿均值） | 14,685 | 96.95% | 96.82% |
| 12,000（到顶） | 16,485 | 97.28% | 97.17% |

**所以 12000 预算下的时间平均 ≈96.8%，只有锯齿顶端那十几轮能站上 97%**——这解释了实测 96.70% 与"最好 10 轮 97.05%"并存。t3 结论里"历史增长即可自然越过 97%"只在**到顶前**成立，到顶后会被压缩拉回。

两种把 97% 变成稳态的办法（择一即可，都不动人设）：

| 杠杆 | 改法 | 效果（按 T=467 算） |
|---|---|---|
| 历史预算 12000→16000 | `.env` 一行，回滚一行 | 锯齿 [11,200, 16,000] → P [15,685, 20,485] → 命中 **97.0%~97.7%，均值 ≈97.3%** |
