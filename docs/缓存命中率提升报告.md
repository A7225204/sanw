## 二、根因（按影响排序）

### 根因 1：长期档案每轮重排 → stable 前缀每轮失效 ★★★★★

日志实测：

```
private_100000000   57 轮 → archive 指纹 57 种（每轮都不重样）
群 1109975771       34 轮 → 33 种
群 362611694        20 轮 → 19 种
```

代码位置：`plugins/ai_group.py:3124`

```python
archive_prompt = ltm.archive_text(mem_scope, query=user_text)   # ← query 传进去了
```

`archive_text()` 内部：

1. `query` 非空 → `_reinforce()` 更新每条命中的 `lu`（最近使用时间）和 `w`（权重）
2. 排序 `_order_key()` 里有 **`_fresh = 2.5 * exp(-age/2)`（依赖 lu）** 和 `_new`（依赖最新 id）
3. `lu` 每轮被刷新 → 排序每轮变 → 档案文本每轮变 → **stable 指纹变 → 整段前缀（3.2k + 后面所有历史）全部失效**

这不是"偶发"：代码注释里写着 2026-10-31 修过一次排序冻结，但 `_fresh` 这一项把 lu 又带回来了，等于没冻结住。

### 根因 2：keepalive 只保了一个 scope ★★★☆☆

```
keepalive 62 次，gid 全为空 → 只对私聊做保活
```

群 scope 没有预热，间隔超过缓存 TTL 就直接 cold（163 次冷启动里绝大多数是群）。

### 根因 3：历史接近预算上限，压缩一旦触发就是整段失效 ★★☆☆☆

`HISTORY_TOKEN_BUDGET_PRIVATE=12000`，实测历史 p50≈11.8k，压缩采用"100% 触发、压到 70% 的滞回"：

- 优点：不是每轮压
- 缺点：**一压，从被裁的第一条开始整段缓存全废**（一次冷调用 ≈ 16k tokens）

## 三、修复方案（按 ROI 排序）

### 方案 A：档案排序彻底冻结（必做）★★★★★

改 `plugins/long_memory.py` 的 `archive_text()`：

| 项 | 现在 | 改成 |
|---|---|---|
| `_reinforce` | query 触发更新 lu/w | 保留（只影响淘汰和相关记忆召回） |
| stable 排序键 | `rank + _fresh(lu) + _new(id)` | **`rank_at_day + _new(id)`**，去掉 `_fresh` |
| query 语义相关 | 已由 `archive_related()` 单独提供 | 不动 |

改完：同一 scope 的档案文本**只在该 scope 新增/删除条目时变**（由夜间 consolidate 决定，一天 1~2 次），不再每轮变。

**预期**：命中率 68.6% → **88~92%**；单次 cold 从 163 次降到 ~10 次。

### 方案 B：keepalive 覆盖活跃群 ★★★☆☆

现在 60 秒 tick 只刷新私聊。改成：给"最近 2 小时内有消息的 scope"各打一次最小 prompt（几十 token），把缓存 TTL 续上。

**预期**：群聊命中率 24~61% → 80%+，冷启动再降 30~50 次/天。
**成本**：每次保活约 30~60 tokens，一天几十次 ≈ 忽略不计。

### 方案 C：历史压缩策略改成"只砍尾巴、不重排" ★★☆☆☆

现状是超预算时从头部砍、整段重拼。可改成：

- 阈值从 100% 提到 110%（允许略超，减少触发频率）
- 压缩时保留最近 N 条不动，只替换更早的部分**为一条摘要**（摘要本身固定不变，位置在历史最前）

**预期**：压缩次数减半；真触发时也只废一次。

### 方案 D：volatile 瘦身 ★★☆☆☆

现在 volatile 1300 tokens 每轮都会变（时间/状态/情绪/念头/梦）。能减的：

| 项 | 现状 | 建议 |
|---|---|---|
| 【今天想起】 | 每天一条，内容固定 | 移到 **stable**（一天变一次） |
| 【别复读】 | 有重复时才出现 | 保持（按需） |
| 【昨夜的梦】 | 私聊每轮都带 | 每天首轮带，之后不带（概率 30%） |

**预期**：volatile 1300 → 800 左右，每轮少 500 tokens 未缓存。

### 方案 E：引擎固定 ★☆☆☆☆

切引擎 = 换一套缓存，等于清零。现在配置是 deepseek 单引擎，无需动。

## 七、方案 A 实施记录（2026-11-04 22:50 已上线）

### 改了什么

`plugins/long_memory.py`：

| 位置 | 改法 |
|---|---|
| 新增 `_stable_rank(it, day)` | 排序用"冻结权重"：`w` 量化到 0.5 档、`lu` 量化到**整天** |
| 档案过滤门槛 | `_item_rank` → `_stable_rank`（日内在同一档，不会因强化把条目挤进/挤出） |
| `archive_text` 排序键 | 去掉 `_fresh = 2.5*exp(-age/2)`（依赖精确 lu，每轮都变），只留 `_stable_rank + _new` |

保留不变：
- `_reinforce()` 照旧更新 `w`/`lu`/`hits`（影响淘汰与【相关记忆】召回）
- `archive_related()` 照旧做语义相关召回（query 相关部分只在这里）
- 新事实加成 `_new`（最新 12 条 +3.2）保留，保证新状态能顶上来
